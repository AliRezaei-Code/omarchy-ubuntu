# Test files that fail on the CI runner for reasons the port does not own, one
# name per line, without the -test.sh suffix.
#
# `./test/all` exits non-zero on any failure, and this tree has carried failures
# like these since before the port started, so a job that requires zero
# failures is permanently red -- and a permanently red build is
# indistinguishable from a broken one, which trains everyone to ignore it.
# `bin/omarchy-ci-suite` compares a run against this list: a new failure fails
# the build. A name here that no longer fails is reported loudly but does not
# fail it, because one run cannot tell "fixed" from "passed by luck".
#
# This is the ubuntu-22.04 runner's baseline, taken from actual runs rather
# than from a developer machine. They are not the same machine, and getting
# that wrong is what the first CI run did: it listed eleven files that pass
# on the runner, and the gate correctly reported the list as stale.
#
# Each entry says why, so a line here is never a mystery.

# --- the target release does not ship the tool -----------------------------
#   bar-text-color  `magick`, i.e. ImageMagick 7. 22.04 packages ImageMagick
#                   6, which has no `magick` at all. The command falls back
#                   rather than refusing, so the test -- which requires the
#                   tool -- is what fails.
#   keybindings-menu  `xkbcli`, which no jammy archive package provides.
#   mise-work-path   `mise`, not in the 22.04 archive.
bar-text-color
keybindings-menu
mise-work-path

# --- the machine the runner is --------------------------------------------
# The tree is not root-owned, so omarchy-plymouth-set refuses to publish. It
# now stops even earlier, on the ImageMagick 7 guard, since 22.04 has no
# ImageMagick 7; either way the run needs something the runner lacks.
plymouth-set
# Hardware the runner does not have.
hw-hybrid-gpu

# --- environment-dependent, not flaky -------------------------------------
# system-sleep-ownership-migration quarantines a path behind a root-only
# directory, and which of its two branches runs depends on the environment
# rather than on the code. It is deterministic either way -- 8 failures in 8
# runs on this workstation, on this drive and on /tmp alike, so it is the
# umask and not the disk. It touches nothing the port changed. The umask-
# driven siblings (hermes-skin-migration, omasnap) and the privileged one
# (nopasswd-sudo-expiry) fail here for the same reason and pass on the runner.
system-sleep-ownership-migration
